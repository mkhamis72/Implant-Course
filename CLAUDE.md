# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Implant Course Manager** — web app for implant-course organizers in Egypt (English UI). Patients with an FDI odontogram, surgical/prosthetic inventory with lot traceability, courses/delegates, surgery schedule plus lecture/workshop talks, checklists, course reports, dashboard; admin/organizer/delegate roles. Spec: `docs/superpowers/specs/2026-10-01-implant-course-manager-design.md`; plans in `docs/superpowers/plans/`.

All code lives in `web/` — run every command from there.

Development, DB and E2E tests run on a **local Supabase stack** (Docker; `web/supabase/config.toml` mirrors prod's auth settings, MFA and email templates; its own migration runner is off, `npm run db:migrate` applies `supabase/migrations`). `web/.env.local` points at it (never print its contents); emails land in Mailpit (http://127.0.0.1:54324). Test fixtures refuse to run unless `ALLOW_TEST_FIXTURES=1` and `TEST_SUPABASE_PROJECT_REF=local` with both URLs on 127.0.0.1/localhost (or a hosted ref matching both URLs) (`scripts/test-guard.ts`). `scripts/db.ts` `pgConfig()` connects to the local stack without TLS and requires `DATABASE_CA_CERT` for hosted projects; hosted `DATABASE_URL` must be the Session pooler URI.

## Architecture

**Stack:** Next.js 15 App Router (server components + server actions), React 19, Tailwind v4, Zod v4, Supabase (`@supabase/ssr`) with Postgres RLS.

**Companies (multi-tenant, part 1):** one Supabase project per company behind one app. `src/lib/tenant/` routes by Host: middleware (Node runtime) → `routeHost()` → registry → sets the trusted `x-tenant` (any browser-sent one is dropped) and that company's CSP. Server code gets it with `currentTenant()`, which also requires the request's Host to belong to that tenant; `createClient()` / `createAdminClient()` (async) use it. Registry: none configured = the `NEXT_PUBLIC_SUPABASE_*` / `SUPABASE_SERVICE_ROLE_KEY` env vars as tenant `default`, serving any host; `TENANTS_FILE` = local list (dev/isolation E2E only); `CONTROL_SUPABASE_URL` = the control project (`tenants`, Vault `tenant/<slug>/…`, cache 60 s, stale ≤ 10 min). Control migrations: `supabase/control/migrations/`, `npm run db:migrate -- --control`. Unknown host 404, suspended 503.

**Console (multi-tenant part 4):** `CONSOLE_HOST` is routed first by `routeConsole` (company hosts 404 on `/console`, the console host serves nothing else). Sign-in is control-project Auth with mandatory TOTP and the `console_admins` list; `requireConsoleAdmin()` guards every console page and action. Writes go through the `console_*` definer functions with the admin's email as `actor` (control migrations 0002, 0003; `console_log` records first-admin create/reset); health is `GET /console/api/health?slug=`. Runbook: `docs/operations.md` §G → Console.

**Branding (multi-tenant part 2, 0040):** each company's name, brand colour, navigation colour and logo live in its own database (`public.branding`, `public.branding_logos`; logo bytes are kept out of `audit_log`, `logo_version` is audited). Anyone reads them through `branding_public()` / `branding_logo()` (the login page renders before sign-in); admins write through `update_branding` / `set_branding_logo` / `clear_branding_logo` (Admin → Settings → Branding). `getBranding()` (`src/lib/branding/get.ts`) reads it once per request and falls back to the defaults on any failure; the root layout sets the title, icon and an `html:root` CSS-variable override (`brandingCss`), and `/brand/logo?v=<version>` (public path) serves the logo. Readability rules are in `src/lib/branding/colors.ts`; status colours are never branded. Nav colours use the `bg-nav` / `text-nav-ink` / `hover:bg-nav-hover` / `border-nav-line` tokens.

**The database is the source of truth for rules.** Every multi-table or integrity-sensitive operation (place implant, fit component, receive stock, corrections, booking, checklists) is a `public.*` plpgsql function called via `supabase.rpc(...)`. Conventions in those functions:
- `security definer set search_path = ''`, first line `perform app_private.require_perm('<area>', 'edit');` (plain `require_active()` only for non-area helpers), explicit `revoke … from public, anon` / `grant … to authenticated`. Readers that should obey RLS are `security invoker`.
- Business errors are raised with `app_private.fail('message')` (hint `'user'`). In TS, `userMessage(error)` (`src/lib/db-errors.ts`) shows those verbatim and hides everything else.
- `public.is_active_user()` / `is_admin()` gate RLS (active profile, plus aal2 when the user has verified 2FA). Writes are further restricted by column-level grants.
- **Roles & permissions** (0029–0034):
  - Roles are `admin`, `organizer` and `delegate`. `is_active_user()` means active **staff** only (admin or organizer).
  - **Organizers:** `user_permissions` holds None/View/Edit per area (`patients`, `schedule`, `courses`, `checklists`, `inventory`, `delegates`).
    - In SQL, `public.can(area, level)` decides access. **Restrictive** `<table>_area_*` policies AND it with the existing policies; write them as `(select public.can(...))` so it runs once per query (0034).
    - Every security-definer write function starts with `app_private.require_perm(area, 'edit')`. `tests/db/permissions.test.ts` fails if a new public definer function or table skips this.
    - Some reads cross areas, for example schedule → patients/courses and patients → bookings; see 0032 and 0033.
    - In TS, pages call `requirePermission(area)`, actions call `requirePermission(area, 'edit')`, and controls hide unless `canEdit(profile, area)`.
  - **Delegates** (`profiles.delegate_id`) get no table access. They read only through `my_schedule()` and `my_report()`, on the `/my` pages.
  - Staff-picker lists (checklist assignee, lead organizer, fitted by organizer) filter `role in ('admin','organizer')`: an active profile may be a delegate login. `check_assignee` enforces it for checklists (0037).
- `app_private.audit_row()` trigger on every table → `audit_log` (patient History tab reads it via `patient_history`). Patients view reads only the patient tables' audit rows; admins read all (0036).
- `stock_movements` is an append-only ledger; corrections are reversing movements. Lock order: site → batch.
- Dates are Cairo dates: use `public.cairo_today()` in SQL, `todayIso()` (`src/lib/dates.ts`) and `formatDate/formatTime` (`src/lib/format.ts`) in TS — never `current_date` / `new Date()` formatting.
- Patients and medical history use optimistic concurrency on `updated_at`.
- Supervisors on bookings and implants (`surgery_slots.supervisor_id`, `implant_sites.supervisor_id`) reference `public.supervisors`, an admin-maintained list of names (Admin → Supervisors), not user accounts. Accounts copied in by 0024 kept their profile id as supervisor id. Embed names via `supervisors!*_supervisor_ref_fkey`. "Fitted by organizer" on components still references `profiles`.
- The catalogue is Oxy Implant PSK-MDK + MD EXT, generated from `docs/catalog/oxy-catalog.csv` (0026). The 0008 sample brands are deactivated (`is_sample`), not deleted. Any component can be fitted without a product (Oxy cover screws come in the implant box). "Final restoration" is no longer offered in the Component form (restorations have their own tab); SQL still accepts the type for the previous app version.
- **Implant picker** (Plan / Place forms, `patients/[id]/implant-picker.tsx` + `src/lib/inventory/implant-picker.ts`):
  - The steps are brand (only when several brands are active), line, type, then size.
  - Line and type are `products.system` split at `" · "` ("PSK-MDK · PSK Micro"). New catalogue rows must keep that format; a system without `" · "` is a line with no type step.
  - "In stock only" counts stock usable on the placement date (`availableLots`).
- **Receiving stock while placing:** with no usable stock, the placement form receives it in place through `receiveStockForPlacement`. That action needs Edit on Inventory (`ChartData.canReceive`) and doesn't redirect, so the typed fields survive the refresh.
- **Patient list filter:** `search_patients(q, include_archived, stages)` takes one array of implant stages (`implant_stage`) and chart states `missing` / `extracted` (`tooth_status`), ORed (0041). Its options are in `src/lib/patients/stages.ts`. The `prosthetic` stage still exists in SQL but isn't offered. It also accepts the scan filters `digital_scan` / `conventional` / `impression_pending` (0054).
- `implant_sites.technique` is `guided` / `free_hand`, nullable in the DB (older rows and the previous app version) but required by the app's Zod schemas; the schedule colours bookings by it (`bookingTechnique`). Bookings are edited in place with `update_surgery_slot` (same day only) and completed/reopened with `set_slot_status` (0027). Bookings need a surgery session that day: Schedule editors add one from the Schedule page ("Add surgery day") through `add_surgery_session`, which needs Edit on Schedule and only creates `surgery` sessions (0039); other session types are still added under Courses (Edit on Courses).
- **Placement and course reports (0035).**
  - The app places implants with `place_implant_v3` (0060): the old placement function plus a required `p_course` (the Place form's Course select, running courses first; `correct_placement_v2` does the same for Corrections). `place_implant_v2` and `correct_placement` were dropped in 0063. The Place form doesn't capture torque, ISQ or bone type: they are recorded in Surgical details through `save_implant_surgery_v2` (0053; 0055 skips the implant update when they are unchanged). The old `save_implant_surgery` was dropped in 0056.
  - The old 13-argument `place_implant` was dropped in 0052. Don't add an overload of a function with defaulted parameters: PostgREST's named-argument calls become ambiguous.
  - `course_report(course)` is security invoker, so implants show only to users with Patients or Schedule view. The report's summaries and CSV are built in `src/lib/reports/course-report.ts`.
- **Restorations (0057–0061).** `restorations` (stage `temporary`/`final`; type single crown / bridge / overdenture / full arch; teeth covered; fitted date; retention, material, delegate, supervisor, course, notes; end: `ended_on`, `end_kind` `replaced`/`remade`, `end_reason`), `restoration_sites` (the implants it sits on) and `restoration_problems` (chipping, fracture, debonding, screw loosening/fracture, wear, other, with action taken). Written only through `add_restoration` / `update_restoration` / `void_restoration` and `record|update|void_restoration_problem` (optimistic on `updated_at`). Rules are in SQL and mirrored for the form in `src/lib/restorations/`: a single crown has one implant, the others at least two; all implants placed, the patient's and in one jaw; teeth covered are one contiguous run in arch order that includes every implant tooth (cantilevers extend it); fitted date today or earlier and not before an implant's `placed_on`. Adding one ends every current restoration on its implants (`replaced` for a temporary; a final ended by a final is `remade` and needs a reason); a temporary over a final is refused (record a problem instead). The database owns `implant_sites.state = restored`: an implant is restored exactly while it has a current, non-voided final restoration, and the tooth status follows. Loading (immediate ≤ 7 days after placement, early ≤ 2 months, else conventional) is derived in TS only (`LOADING_IMMEDIATE_DAYS`, `LOADING_EARLY_MONTHS`). Problems belong to the restoration; the implant complication form no longer offers the crown types (`screw_loosening`, `screw_fracture`, `restoration_fracture`, `loss_of_retention`, `prosthetic_remake`) though SQL still accepts them. 0059 converted existing `final_restoration` components into restoration records (existing rows only, nothing seeded). Readers: `course_restorations(course)` (course report table and the per-delegate Restored count), `my_restorations()` and `delegate_restorations(delegate)` (delegate reports; a restoration's course is `course_id`, else the course containing `fitted_on` where its delegate is enrolled), and `course_options()` (0061: courses for the pickers, View on Patients). UI: `patients/[id]/restorations.tsx` (Restoration tab), odontogram bars ("Bridge 34–36"; the first tap on a covered tooth opens its restoration, the second selects the tooth).
- **Scan / impression (0054).** `implant_sites.impression_type` (digital scan / conventional) and `impression_taken_on` are written only through `record_impression` (optimistic on `updated_at`); empty means not taken. UI: `ImpressionControl` on the Implant tab (`patients/[id]/impression-control.tsx`), labels in `src/lib/implants/impression.ts`; patient-list filter values are in the Patient list filter bullet.
- **Research capture (0043–0044).** Medical-history risk factors are yes / no / not assessed (`null`): `smoking`, `diabetes_status`, `*_status`, `periodontitis_history`, `bruxism`, `previous_implant_failure`, plus `hba1c`/`hba1c_date`, `cigarettes_per_day` (`src/lib/patients/risk-factors.ts`). The old booleans (`diabetes`, `smoker`, …) were dropped in 0050; `medical_history_check` refuses a future HbA1c date. History labels for the old columns stay in `src/lib/patients/history.ts` for older entries. Placed implants have one `implant_surgery` row (timing, extraction date, phenotype, mucosa, flap, torque type, healing, closure, grafting performed) and any number of `implant_grafts`, written through `save_implant_surgery_v2` (0053; optimistic on `updated_at`; it also records insertion torque, ISQ and bone type on `implant_sites`, so Surgical details completeness counts 12 fields) / `add|update|delete_implant_graft`; rules and labels in `src/lib/implants/surgery.ts`, UI in `patients/[id]/surgical-details.tsx`. An empty value means not recorded — never treat it as "no". Roadmap of later research parts: `docs/superpowers/specs/2026-10-17-research-capture-surgery-design.md`.
- **Follow-up visits (0045–0046).** `implant_followups` rows are visits: scheduled (`visit_key`: `early_review`, `osseointegration`, `month_6`, `month_12`, `year_N`) or unscheduled (null), with `attendance` and findings (pain, swelling/suppuration/plaque/mobility, four-site probing and bleeding, ISQ, prosthesis, radiograph). Recorded only through `record_visit` (findings as one jsonb, validated in SQL; not editable — void and re-record). The schedule is `visit_schedule()`; status (upcoming / due / overdue / missed / done / did not attend / not needed) is calculated only in SQL by `implant_visits(patient)` and `recall_list()` (security invoker, View on Patients) — never recompute it in TS. Rules in `src/lib/visits/`, UI in `patients/[id]/visits.tsx`, recall page `/patients/recall`. `record_followup` was dropped in 0051; failures recorded through it have no details until `record_failure` adds them (DB tests recreate such rows with `legacyFailure`). `app_private` functions can't be called from security-invoker functions (no schema usage for `authenticated`).
- **Radiographs (0064–0065).** `radiographs` (date, type `periapical`/`cbct`, purpose `planning`/`baseline`/`loading`/`follow_up`/`other`, teeth, optional link and notes) and `radiograph_bone_levels` (one row per implant: `mesial_mm`, `distal_mm`) are written only through `save_radiograph` (optimistic on `radiographs.updated_at`) and `void_radiograph` (reason required; voided rows hidden everywhere); `radiographs_for(patient)` reads them. `save_radiograph` replaces the whole measurement set, so the form must send every implant's values or the omitted ones are deleted (the form refuses to untick a measured tooth); since 0065 it upserts, deleting only implants no longer measured and updating only changed values, so an edit adds no History noise. Rules: date today or earlier (before placement is allowed); 1+ valid FDI teeth, no duplicates; baseline / loading / follow-up need an implant placed by the date on one of the teeth; a level can only be on a placed / restored / failed implant on one of the X-ray's teeth, placed on or before the X-ray's date (0065); levels are -5.0 to 15.0 mm, positive = bone below the shoulder, null = not measured (never 0), each row needs mesial or distal; link must be http(s) and opens in a new tab. UI: patient "X-rays" tab (`patients/[id]/xrays/`, Add / Edit / Remove) and the "X-rays" tab in an implant's tooth panel (`implant-xrays.tsx`, reuses `XrayCard` with `onlySite`, so edits still carry every implant's levels); labels and rules in `src/lib/radiographs/`; History labels in `src/lib/patients/history.ts`.
- **Outcomes and data quality (0066–0068).** Outcome readers have no UI until 5b; data quality has a page and badges. All are security invoker with View on Patients: `outcomes_version()` (`'outcomes-v1'`), `icoi_grade(...)` (the ICOI cut-offs are constants inside it and nowhere else; owner rule: mobility or pain ≥ 4 grades IV and, with pain/mobility/suppuration recorded, a III sign grades III without an X-ray — only a possible I/II needs bone loss), `visit_grades`, `implant_outcomes` (survival means still in the mouth: `lost` / `removed` are events, `failed_in_place` survives; censored at the latest contact, milestones at loading / 1 year / year N: `failed` / `survived` / `not_reached` (milestone still in the future) / `unknown` (lost to follow-up); owner rule: a legacy failure with no `failed_on` is dated by its earliest failed visit, and only without one is it `event_time_unknown`; `latest_grade_reason` names what set the latest grade), `survival_at`, `crown_outcomes` (event = `end_kind = 'remade'`; implant events dated the same way) and `data_quality_issues(patient)` (impossible dates only: a visit, complication, restoration, non-planning X-ray or `failed_on` before placement, any of those in the future, a restoration problem before its fitting). Status is decided only in SQL. UI: `/patients/data-quality` (link next to Recall list; rows sorted by `sortIssues` in `src/lib/data-quality/issues.ts`), "Date problem" badges on the patient header and tooth panel.
- **Research page (0069).** `research` is a permission area with None / View only levels (`set_user_permissions` refuses edit); admins always have it, new organizers default to None (`default_permissions()` skips it), delegates never. `implant_outcomes_detail` / `crown_outcomes_detail` are security invoker readers gated on `public.can('research','view')` and also need View on Patients. Summaries and Kaplan–Meier are pure TS over those rows in `src/lib/research/summary.ts` (survival = survived / (survived + failed), shown as "N of M" with not reached and lost to follow-up; under 30 = small sample); filters, labels and drill-down selection are in `src/lib/research/view.ts`. UI: `/patients/research` (tiles, inline-SVG survival curve, ICOI bars, complications) and `/patients/research/drilldown?list=<key>&filters` (patient lists behind each number); the patients list shows a Research link only with Research view.
- **Research export (0070).** `GET /patients/research/export?format=xlsx|csv&<research filters>` (403 without Research view and Patients view, 400 bad input, 500 failure) returns an anonymised workbook or CSV zip (`research-export-YYYY-MM-DD.xlsx|.zip`, Cairo date) for the implant set of `implant_outcomes_detail` with the page's filters. Eight tables (`implants`, `patients`, `visits`, `radiographs`, `complications`, `restorations`, `restoration_problems`, `grafts`) come from eight security-invoker readers and are paged past the 1000-row cap (`fetchAll`). **Allowlist rule:** every exported column has an entry in `DICTIONARY` (`src/lib/research/export/dictionary.ts`) and the builders refuse anything else; adding a column requires a dictionary entry, free text never (no notes, reasons, other-details, radiograph links, names, phone, email, address, file number, dob). Entities are identified by random study codes (`P-` patient, `I-` implant, `R-` restoration, `D-` delegate, `S-` supervisor, `C-` course; 6 characters, stored once in `app_private.research_codes` and reused). The route first calls `assign_research_codes(filters)` (one insert ordered by entity, id, so concurrent exports can't deadlock), then runs the readers one at a time, ordered date column first (`exportOrder`); the files show the course/delegate filters as codes, raw ids only in the log. Every export is recorded by `log_research_export` in `research_exports` (admins read it; shown as Recent exports on the Research page). The file carries a confidentiality note (`about` sheet / `README.txt`). Spec: `docs/superpowers/specs/2026-10-23-research-export-design.md`.
- **Statistics (0071).** Research tiles show the Kaplan–Meier estimate at day 365 / 730 with a log-log 95% CI (Greenwood, as R `survfit`) and the number at risk; time is `follow_up_days / 30.4375` months, implants with `event_time_unknown` are left out (and counted). KM, log-rank (as R `survdiff`) and thin-data rules are pure TS in `src/lib/research/stats.ts` (fixture from published R values) and `groups.ts`. **Compare by** (`compare=` brand / technique / loading / smoking / diabetes / periodontitis / bone_type) reads the group variables from `implant_outcomes_groups` (0071, security invoker, Research + Patients view); "Not assessed" is its own group, shown but never tested; loading (part-3 constants via `loadingFrom`) gets a table only, no test. Owner principle: always show numbers; thin = < 30 at risk, < 10 failures in a test or a group < 5 → `⚠ Not enough data …`; "—" only when undefined. `src/lib/research/export/analysis.R` (base R + `survival`; KM, `survdiff`, loading table, Cox stratified by course + placing delegate, patient-clustered SEs, EPV warning) ships in the CSV zip and at `/patients/research/analysis.R` (Research view); it may use only `DICTIONARY` columns plus its `DERIVED` list (`analysis.test.ts`), and is read from disk at run time (`outputFileTracingIncludes` in `next.config.ts`). Spec: `docs/superpowers/specs/2026-10-23-statistics-design.md`.
- **Complications and failure (0047–0048).** `implant_complications` (category → type, noticed/resolved dates, severity, treatment, optional visit link) are written through `record_complication` / `update_complication` (optimistic on `updated_at`) / `void_complication` (details as jsonb, validated in SQL); open = no resolved date; open ones mark the tooth on the odontogram. Failure lives on `implant_sites` (`failed_on`, `failure_type`, `failure_reason`, `failure_notes`): a "failed" visit must carry the details (`record_visit` → `app_private.apply_failure`), old failures get them through `record_failure`, edits through `correct_failure` (optimistic on `implant_sites.updated_at`); voiding the failed visit clears them. Early vs late is derived in TS (`src/lib/implants/failure.ts`), never stored. Visits of a failed implant stop at the failure date. Peri-implantitis/mucositis are clinician-recorded; the form only shows the 2017 case definitions.
- **Lectures & workshops (0028):** `sessions.type` lecture/workshop sessions hold `talks` (time, `lecturers` row, topic), written only via `create_talk` / `update_talk` / `delete_talk`, which refuse times outside the session, overlaps in the session and double-booked lecturers. UI: `schedule/lectures|workshops`, sharing `schedule/_talks/`. Sessions have an optional `room`.
- Courses and patients are hard-deleted only through `delete_course` / `delete_patient`, which refuse anything with stock traceability or placed implants (the ledger is permanent); otherwise patients are archived. Users and delegates likewise only through `delete_user` (admin; any FK to the profile = "has records") / `delete_delegate` (refuses implant records or bookings) (0037); the action then deletes the Auth account with the service role (`src/lib/admin/auth-accounts.ts`), which also sets one-time passwords for **Reset password**. Users can also reset their own password from the login page (**Forgot password?** → `/login/forgot`, shown only while `EMAIL_ENABLED`): the reply never reveals whether the address has an account; the recovery link sets the `icm_reset_pending` cookie (15 min) so a 2FA user goes `/login/mfa` → `/account/set-password` (`src/lib/auth/password-reset.ts`).
- Tooth state `extracted` is labelled "To be extracted" (the tooth is still present); the enum value is unchanged.

**Migrations** (`web/supabase/migrations/NNNN_*.sql`) are applied once, in order, by `scripts/migrate.ts`; never edit an applied one. To change a function, add a new migration with `create or replace` of the *latest* definition (search later migrations — functions are redefined several times). Keeping the signature keeps its grants and avoids a new overload; widen what an existing parameter accepts (as 0041 does with `stages`) rather than adding a defaulted one. New public tables get no privileges by default (0019) and must grant what they need.

Releases (`.github/workflows/release.yml`) migrate production *before* the new code deploys, so the previous app version runs against the new schema for a few minutes: migrations must be backward-compatible (add, don't rename or drop in the same release). When something the previous version still uses must go (e.g. an FK it embeds through), ship two PRs: the additive one first, the removal after it has deployed (see 0024 → 0025).

**App layout:** `src/app/(app)/` is the signed-in area; its `layout.tsx` redirects to `/login` or `/deactivated` and shows delegates their own menu. Because pages render in parallel with layouts, pages and every server action must guard themselves (`src/lib/auth/session.ts`): `requirePermission(area[, 'edit'])` for panel pages/actions, `requireAdmin()` for admin, `requireSignedIn()` for pages shared with delegates (account/security, set-password), `requireDelegate()` for `/my`. `requireActiveUser()` means staff and sends delegates to `/my`. `searchParams` are read with `readParams()` (`src/lib/search-params.ts`), which tolerates repeated params. Domain logic (parsing, labels, schemas, pure helpers) lives in `src/lib/<domain>/` with colocated tests; route folders hold pages, client forms and `actions.ts`.

**Security headers:** `next.config.ts` applies `securityHeaders()` (`src/lib/security-headers.ts`) to every route — a CSP allowing only this site and the Supabase project. Any new external origin (script, image, API) must be added there or the browser blocks it.

**Styling:** design tokens live in `src/app/globals.css` (`@theme`). Use the named colours (`text-muted`, `border-line`, `text-accent`, `bg-ok-soft`, `text-bad` …), not raw Tailwind palette colours, and the shared classes `.btn`/`.btn-secondary`/`.btn-danger`, `.input`, `.label`, `.card`, `.badge(-ok|-warn|-bad)`, `.rule(-ok|-warn|-bad|-accent)`, `.page-header`, `.tabs`/`.tab` (or `SectionNav`). Data tables use `className="table"` with `data-label` on every `<td>` so they stack on phones.

## Tests

- **DB tests** (`tests/db/`): each test runs in `withTx` (always rolled back); `actAs(c, userId)` impersonates a user via JWT claims, `asPostgres(c)` resets role; `setPerms(c, user, {...})` sets area permissions. Test users come from `inject('testUsers')` (`tests/support/test-users.ts`): `organizer` is pinned to Edit everywhere, `viewer` has View everywhere + Edit on Inventory, `delegate` is a delegate login linked to the "Test Delegate Login" delegate.

## Gotchas

- Windows + Git Bash: heredocs and `node -e` mangle backslashes/quotes — write files containing `\` with the Write/Edit tools. Files are CRLF in git; multi-line string matches may need CRLF normalisation.
- `gh` is not on Git Bash's PATH: call `"/c/Program Files/GitHub CLI/gh.exe"`. The user's `!` prompt runs Bash, not PowerShell. There is no Python; script with Node.
- The local stack needs Docker Desktop running and `npm run db:start` after every reboot; `test:db`, E2E and `next dev` fail to connect otherwise (`ship.sh verify` checks it first). `npm run db:stop` frees its memory.
- E2E reuses whatever listens on :3000. A leftover `next dev` (find it with `Get-NetTCPConnection -LocalPort 3000`) can hold several GB and make unrelated specs time out — check memory before debugging timeouts.
- E2E patients with stock movements survive teardown, so DB tests that search by name must use names unique to the test (e.g. `Zz …`). `slot-placement` E2E occasionally clashes with a leftover booking on its random future date; rerun before investigating.
- The booking form only lists surgery sessions dated today or later.
- React 19 resets `<form action={…}>` after the action: keep inputs uncontrolled with `defaultValue={valueOf(state, …)}` (`src/lib/patients/form-state.ts`) so values survive. `<select>` and radios still fall back to their first/initial option — remount them on each result (`key`; see `schedule/_talks/talk-form.tsx`, `admin/users/permission-grid.tsx`).
- `npm run test:db` applies pending migrations to the local stack on its first run; treat applied migrations as uneditable anyway (prod applies each once). Write the failing test before creating the migration file, and dry-run a new migration in a rolled-back transaction (a small `tsx` script using `pgConfig()`, run with `NODE_PATH=web/node_modules`) before the first `test:db`.
- One-off `tsx` scripts kept outside `web/` (scratchpad): name them `.ts`, not `.mts`, and wrap the body in an async function (no top-level await); import `web/scripts/load-env` and the helpers by absolute path; run with `ENV_FILE=… NODE_PATH=web/node_modules npx tsx <file>`.
- Supabase Auth failures reach users only as "Something went wrong" (`mapAuthError`, `src/lib/auth/errors.ts`). The real cause is in Supabase → Logs → Auth → the entry → **Raw** (e.g. an invite failing with SMTP `550 … domain is not verified` was a Resend key from the wrong account).
- The full E2E run (~110 tests) exceeds the 10-minute foreground limit and background runs get killed under memory pressure: run it in parts (`npx playwright test <spec names…>`) and check free memory first.
- Next.js renders a hidden `role="alert"` route announcer: filter alert locators by text (`getByRole('alert').filter({ hasText })`).
- There is no Prettier config — don't run Prettier; it rewrites quotes and wrapping.
- A migration that seeds rows must add its table to the restore `TRUNCATE` in `docs/operations.md` §D, or restoring the nightly data-only dump fails on the primary key (as `branding` would have, and `audit_log` did in the 2026-10-08 rehearsal). To find them, migrate an empty stack and list the non-empty tables in `public`, `app_private` and `auth`.
