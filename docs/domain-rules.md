# Domain rules

Feature-level rules for the Implant Course Manager, split out of `CLAUDE.md` to keep it short. Read the section for the area you are changing; the database functions named here are the source of truth (search later migrations for the latest definition).

- Supervisors on bookings and implants (`surgery_slots.supervisor_id`, `implant_sites.supervisor_id`) reference `public.supervisors`, an admin-maintained list of names (Admin → Supervisors), not user accounts. Accounts copied in by 0024 kept their profile id as supervisor id. Embed names via `supervisors!*_supervisor_ref_fkey`. "Fitted by organizer" on components still references `profiles`.
- The catalogue is Oxy Implant PSK-MDK + MD EXT, generated from `docs/catalog/oxy-catalog.csv` (0026). The 0008 sample brands are deactivated (`is_sample`), not deleted. Any component can be fitted without a product (Oxy cover screws come in the implant box). "Final restoration" is no longer offered in the Component form (restorations have their own tab); SQL still accepts the type for the previous app version.
- **Implant picker** (Plan / Place forms, `patients/[id]/implant-picker.tsx` + `src/lib/inventory/implant-picker.ts`):
  - The steps are brand (only when several brands are active), line, type, then size.
  - Line and type are `products.system` split at `" · "` ("PSK-MDK · PSK Micro"). New catalogue rows must keep that format; a system without `" · "` is a line with no type step.
  - "In stock only" counts stock usable on the placement date (`availableLots`).
- **Receiving stock while placing:** with no usable stock, the placement form receives it in place through `receiveStockForPlacement`. That action needs Edit on Inventory (`ChartData.canReceive`) and doesn't redirect, so the typed fields survive the refresh.
- **Patient list filter:** `search_patients(q, include_archived, stages)` takes one array of implant stages (`implant_stage`) and chart states `missing` / `extracted` (`tooth_status`), ORed (0041). Its options are in `src/lib/patients/stages.ts`. The `prosthetic` stage still exists in SQL but isn't offered. It also accepts the scan filters `digital_scan` / `conventional` / `impression_pending` (0054).
- `implant_sites.technique` is `guided` / `free_hand`, nullable in the DB (older rows and the previous app version) but required by the app's Zod schemas; the schedule colours bookings by it (`bookingTechnique`). Bookings are edited in place with `update_surgery_slot` (same day only) and completed/reopened with `set_slot_status` (0027). Bookings need a surgery session that day: Schedule editors add one from the Schedule page ("Add surgery day") through `add_surgery_session`, which needs Edit on Schedule and only creates `surgery` sessions (0039); other session types are still added under Courses (Edit on Courses).
- **Placement and course reports (0035).**
  - The app places implants with `place_implant_v3` (0060): the old placement function plus a required `p_course` (the Place form's Course select, running courses first; `correct_placement_v2` does the same for Corrections). `place_implant_v2` and `correct_placement` were dropped in 0063. The Place form doesn't capture torque, ISQ or bone type: they are recorded in Surgical details through `save_implant_surgery_v2` (0053; 0055 skips the implant update when they are unchanged). The old `save_implant_surgery` was dropped in 0056.
  - The old 13-argument `place_implant` was dropped in 0052. Don't add an overload of a function with defaulted parameters: PostgREST's named-argument calls become ambiguous.
  - `course_report(course)` is security invoker, so implants show only to users with Patients or Schedule view. The report's summaries and CSV are built in `src/lib/reports/course-report.ts`.
- **Restorations (0057–0061).** `restorations` (stage `temporary`/`final`; type single crown / bridge / overdenture / full arch; teeth covered; fitted date; retention, material, delegate, supervisor, course, notes; end: `ended_on`, `end_kind` `replaced`/`remade`, `end_reason`), `restoration_sites` (the implants it sits on) and `restoration_problems` (chipping, fracture, debonding, screw loosening/fracture, wear, other, with action taken). Written only through `add_restoration` / `update_restoration` / `void_restoration` and `record|update|void_restoration_problem` (optimistic on `updated_at`). Rules are in SQL and mirrored for the form in `src/lib/restorations/`: a single crown has one implant, the others at least two; all implants placed, the patient's and in one jaw; teeth covered are one contiguous run in arch order that includes every implant tooth (cantilevers extend it); fitted date today or earlier and not before an implant's `placed_on`. Adding one ends every current restoration on its implants (`replaced` for a temporary; a final ended by a final is `remade` and needs a reason); a temporary over a final is refused (record a problem instead). The database owns `implant_sites.state = restored`: an implant is restored exactly while it has a current, non-voided final restoration, and the tooth status follows. Loading (immediate ≤ 7 days after placement, early ≤ 2 months, else conventional) is derived in TS only (`LOADING_IMMEDIATE_DAYS`, `LOADING_EARLY_MONTHS`). Problems belong to the restoration; the implant complication form no longer offers the crown types (`screw_loosening`, `screw_fracture`, `restoration_fracture`, `loss_of_retention`, `prosthetic_remake`) though SQL still accepts them. 0059 converted existing `final_restoration` components into restoration records (existing rows only, nothing seeded). Readers: `course_restorations(course)` (course report table and the per-delegate Restored count), `my_restorations()` and `delegate_restorations(delegate)` (delegate reports; a restoration's course is `course_id`, else the course containing `fitted_on` where its delegate is enrolled), and `course_options()` (0061: courses for the pickers, View on Patients). UI: `patients/[id]/restorations.tsx` (Restoration tab), odontogram bars ("Bridge 34–36"; the first tap on a covered tooth opens its restoration, the second selects the tooth).
- **Scan / impression (0054).** `implant_sites.impression_type` (digital scan / conventional) and `impression_taken_on` are written only through `record_impression` (optimistic on `updated_at`); empty means not taken. UI: `ImpressionControl` on the Implant tab (`patients/[id]/impression-control.tsx`), labels in `src/lib/implants/impression.ts`; patient-list filter values are in the Patient list filter bullet.
- **Research capture (0043–0044).** Medical-history risk factors are yes / no / not assessed (`null`): `smoking`, `diabetes_status`, `*_status`, `periodontitis_history`, `bruxism`, `previous_implant_failure`, plus `hba1c`/`hba1c_date`, `cigarettes_per_day` (`src/lib/patients/risk-factors.ts`). The old booleans (`diabetes`, `smoker`, …) were dropped in 0050; `medical_history_check` refuses a future HbA1c date. History labels for the old columns stay in `src/lib/patients/history.ts` for older entries. Placed implants have one `implant_surgery` row (timing, extraction date, phenotype, mucosa, flap, torque type, healing, closure, grafting performed) and any number of `implant_grafts`, written through `save_implant_surgery_v2` (0053; optimistic on `updated_at`; it also records insertion torque, ISQ and bone type on `implant_sites`, so Surgical details completeness counts 12 fields) / `add|update|delete_implant_graft`; rules and labels in `src/lib/implants/surgery.ts`, UI in `patients/[id]/surgical-details.tsx`. An empty value means not recorded — never treat it as "no". Roadmap of later research parts: `docs/superpowers/specs/2026-10-17-research-capture-surgery-design.md`.
- **Follow-up visits (0045–0046).** `implant_followups` rows are visits: scheduled (`visit_key`: `early_review`, `osseointegration`, `month_6`, `month_12`, `year_N`) or unscheduled (null), with `attendance` and findings (pain, swelling/suppuration/plaque/mobility, four-site probing and bleeding, ISQ, prosthesis, radiograph). Recorded only through `record_visit` (findings as one jsonb, validated in SQL; not editable — void and re-record). The schedule is `visit_schedule()`; status (upcoming / due / overdue / missed / done / did not attend / not needed) is calculated only in SQL by `implant_visits(patient)` and `recall_list()` (security invoker, View on Patients) — never recompute it in TS. Rules in `src/lib/visits/`, UI in `patients/[id]/visits.tsx`, recall page `/patients/recall`. `record_followup` was dropped in 0051; failures recorded through it have no details until `record_failure` adds them (DB tests recreate such rows with `legacyFailure`). `app_private` functions can't be called from security-invoker functions (no schema usage for `authenticated`).
- **Complications and failure (0047–0048).** `implant_complications` (category → type, noticed/resolved dates, severity, treatment, optional visit link) are written through `record_complication` / `update_complication` (optimistic on `updated_at`) / `void_complication` (details as jsonb, validated in SQL); open = no resolved date; open ones mark the tooth on the odontogram. Failure lives on `implant_sites` (`failed_on`, `failure_type`, `failure_reason`, `failure_notes`): a "failed" visit must carry the details (`record_visit` → `app_private.apply_failure`), old failures get them through `record_failure`, edits through `correct_failure` (optimistic on `implant_sites.updated_at`); voiding the failed visit clears them. Early vs late is derived in TS (`src/lib/implants/failure.ts`), never stored. Visits of a failed implant stop at the failure date. Peri-implantitis/mucositis are clinician-recorded; the form only shows the 2017 case definitions.
- **Lectures & workshops (0028):** `sessions.type` lecture/workshop sessions hold `talks` (time, `lecturers` row, topic), written only via `create_talk` / `update_talk` / `delete_talk`, which refuse times outside the session, overlaps in the session and double-booked lecturers. UI: `schedule/lectures|workshops`, sharing `schedule/_talks/`. Sessions have an optional `room`.
- Courses and patients are hard-deleted only through `delete_course` / `delete_patient`, which refuse anything with stock traceability or placed implants (the ledger is permanent); otherwise patients are archived. Users and delegates likewise only through `delete_user` (admin; any FK to the profile = "has records") / `delete_delegate` (refuses implant records or bookings) (0037); the action then deletes the Auth account with the service role (`src/lib/admin/auth-accounts.ts`), which also sets one-time passwords for **Reset password**. Users can also reset their own password from the login page (**Forgot password?** → `/login/forgot`, shown only while `EMAIL_ENABLED`): the reply never reveals whether the address has an account; the recovery link sets the `icm_reset_pending` cookie (15 min) so a 2FA user goes `/login/mfa` → `/account/set-password` (`src/lib/auth/password-reset.ts`).
- Tooth state `extracted` is labelled "To be extracted" (the tooth is still present); the enum value is unchanged.
