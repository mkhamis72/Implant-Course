# Implant Passport — design

Date: 2026-11-24 · Project D of the advanced-rehabilitation request (A implant types, B components/screws, C full-arch view and cases, clean-up all released). Status: draft for owner approval.

## Why
A patient leaves the clinic with implants, components, screws and bridges that a dentist elsewhere — years later — must be able to maintain: which implant, which screw, which screwdriver, what torque. Today that knowledge lives only in the app. The owner wants every patient to have an **Implant Passport**: a professional PDF generated from the existing records (no re-entry), handed to the patient, regenerated when the record changes, with every generated copy **kept as a fixed PDF** so the clinic can show exactly what was handed over and when.

## Owner decisions
- Kept as **fixed PDFs**: each generated passport is stored unchanged with its date, version and who generated it.
- **English now, Arabic later**: written for dental professionals in English; built so Arabic labels can be added in a later release.
- **Built on the server** (approach 1): the server builds the PDF with a PDF library and stores the exact file; download returns those bytes.

## Goals
- Patient page action **"Implant passport"** → a passport page: Generate new passport; list of generated versions (number, date, generated by, size) each with Download; latest first.
- The PDF contains, from existing records only:
  1. **Header:** clinic (company) name and logo (branding), "Implant Passport", passport number `<file no>-<version>` (e.g. P00123-3), generation date (Cairo), page numbers on every page.
  2. **Patient:** name, file number, date of birth (or "Not recorded"), sex if recorded. **Medical section** per the clinic setting (see Owner answers).
  3. **Overview:** implants count by status, restorations count, full-arch cases; a **chart picture**: the schematic full-arch drawing (both arches, implants by type and angle, bridges), with "Schematic drawing — not a substitute for CBCT or 3D planning."
  4. **Implants table** (one row each, arch order): tooth / emergence position, type, brand and system, diameter × length, connection, placed date, status.
  5. **Per implant:** product (brand, system, ref code), implant kind / type, angle and direction, anchorage, entry point, trajectory (when recorded), planned product when different ("Planned: …"), placed date, placed by (doctor or delegate name), lot number (when Inventory is on and recorded), insertion torque and ISQ (when recorded), grafts (type, when recorded), current status (planned / placed / restored / failed).
  6. **Components and screws per implant:** current items by role (healing, abutment, abutment screw, prosthetic screw) with product, ref, connection, gingival height, angle, material, **screwdriver** (interface, size, ref), **recommended torque** and **actual torque**, fitted date; a short replacement history (replaced items with dates).
  7. **Restorations:** type, temporary / final, teeth covered, supporting implants, material, retention, fitted date, status (current / replaced / remade).
  8. **Full-arch cases:** arch, configuration and name, status, implants, temporary and final bridge delivery dates, stages (scan, lab and design with lab name, try-in with passive fit), prosthetic screws of the case implants.
  9. **Footer note:** "This passport summarises the clinic's records on the date shown. It is not a manufacturer warranty or guarantee. Values not recorded are shown as 'Not recorded'."
- Missing values always print **"Not recorded"**, never blank or invented.
- Every generation is stored and audited; every **download** of a stored passport is logged (who, when).

## Non-goals
- Arabic text (later release; the layout keeps labels in one place so they can be translated).
- Emailing or sharing links; public links (none, by design).
- Editing a generated passport; deleting single versions (they go only with the patient, via `delete_patient`).
- Subperiosteal frameworks (not recorded yet).

## Anti-goals
- Any value not taken from the record. No re-entry forms.
- Exposing one company's passports to another, or to users without access to Patients.
- Changing existing clinical screens or rules.

## Approaches (owner chose 1)
1. **Server-built PDF, stored file (chosen).** `@react-pdf/renderer` in a server route builds the PDF from data read with the signed-in user's own client (RLS applies); the bytes are saved through a definer function into a closed table (like consent files, 0072) and served back unchanged.
2. Frozen data + browser print — rejected by the owner: the file would be made on each device; only content, not the file, is kept.
3. Headless browser on the server — rejected: too heavy for Vercel Hobby limits.

## Design
**Database (migration 0145)**
- `public.patient_passports`: `id`, `company_id` (doctors pattern, 0114), `patient_id` (FK, `on delete cascade`), `version int` (1, 2, … per patient; unique `(company_id, patient_id, version)`), `generated_at timestamptz default now()`, `generated_by uuid` (profile), `size_bytes int`, `sha256 text`. Readable by staff with View on Patients (restrictive `can('patients','view')`, company policies).
- `app_private.patient_passport_files` (or a closed `public` table like 0072's consent files): `passport_id`, `company_id`, `bytes bytea` (PDF magic `%PDF-` checked, ≤ 5 MB). Closed to every role; read only through the definer reader.
- `public.passport_downloads`: `passport_id`, `company_id`, `downloaded_at`, `downloaded_by` — append-only log.
- `save_patient_passport(p_patient uuid, p_file bytea) returns uuid` — Edit on Patients; locks the patient row, assigns the next version, stores metadata and bytes, audited.
- `patient_passport_file(p_passport uuid) returns bytea` — View on Patients; logs a download row; company-scoped.
- `delete_patient` keeps working (cascade). Not seeded → no restore TRUNCATE entry. `patient_history` shows "Implant passport generated (version N)".

**App**
- `src/lib/passport/data.ts`: `loadPassportData(patientId)` — one server function gathering patient, medical alerts, sites (products, surgery, grafts, components), restorations, cases and branding with the user's client; pure `passportModel(data)` turning it into printable sections with "Not recorded" filled in (unit-tested without PDF).
- `src/lib/passport/pdf.tsx`: the `@react-pdf/renderer` document (A4, built-in Helvetica, tables with page breaks, header/footer on each page); the chart drawn with react-pdf `Svg` using C1's `fullArchModel` / `implantLine` geometry (no DOM).
- Route `src/app/(app)/patients/[id]/passport/`: page (versions list, Generate button for Edit users) and route handlers `POST …/passport/generate` (requirePermission patients edit → build → `save_patient_passport` → redirect to list) and `GET …/passport/[passportId]/download` (requirePermission patients view → `patient_passport_file` → `application/pdf`, `Content-Disposition: attachment; filename="Implant passport <file no>-<version>.pdf"`, no caching).
- Patient header/tabs: an "Implant passport" link.
- Clinic companies: same (no teaching fields shown; delegate names appear only where recorded).

## Owner answers after the builder check (2026-11-24)
- **Arabic text in the record (Q1 = b):** embed an Arabic-capable font (IBM Plex Sans Arabic, OFL, bundled with the app — no outside fetch; Noto Naskh Arabic was planned, but react-pdf 4.9.0 drops GPOS mark offsets, and Noto Naskh Arabic draws letter dots as marks, so its dots printed beside the word; spike, Task 1) alongside the Latin font, so Arabic names and free text print correctly (right-to-left runs inside the English layout). This also prepares the later Arabic passport.
- **Medical content is a clinic setting (Q2):** Admin → Settings → **Implant passport** with one choice: **Allergies and medications only** (default) / **Full medical summary** (allergies, medications, diabetes, smoker and the other recorded medical-history items) / **Nothing medical**. Stored in `public.passport_settings` (one row per company; no row = the default), written by admins through `set_passport_settings(p_medical text)`. Each generated passport records the level used (`patient_passports.medical_level`) and the PDF shows the section accordingly ("Medical alerts" with "None recorded" when empty; no section at all for Nothing medical).

## Settled calls (mine, incl. builder-check answers)
- **Task 1 is a spike:** build a large synthetic passport (e.g. 16 implants with components and history, two full-arch cases, Arabic name) with `@react-pdf/renderer` in a Node route on the local build and measure time, memory and size against Vercel Hobby limits; fallback `pdfkit` if it does not fit. The owner hears before any change of approach.
- **Size:** ≤ 5 MB stored; above it the save is refused with "The passport is too large to store." The logo is embedded once per PDF.
- **Transport:** the PDF bytes go to `save_patient_passport` through the RPC as `bytea` (the consent upload already does this); the spike measures a realistic size.
- **Stale marker:** the latest version shows "Records changed since this version" when any audit row of the patient's records is newer than its `generated_at`.
- **Fields not recorded by the app are omitted** (no new clinical fields); recorded-but-empty values print "Not recorded".
- **Stored copies never change**, whatever later plan or permission changes.
- Archived patients can generate passports.
- The Generate button is disabled while generating; a duplicate from a retry is acceptable.
- `passport_downloads` goes with the patient (cascade); each version shows "Downloaded N times, last by <name> on <date>".
- Generate needs **Edit** on Patients; view list and download need **View**.
- Contact details (phone, email, address) are **not** printed (privacy; the request says "if authorized" — can be added later as an option).
- Placed-by prints the doctor's name, else the delegate's name, else "Not recorded"; supervisors are not printed.
- Lot numbers print only when the company's plan has Inventory.
- A4 portrait; bundled fonts only (static Noto Sans Regular/Bold + IBM Plex Sans Arabic Regular/Bold), no external font fetch, CSP unchanged.
