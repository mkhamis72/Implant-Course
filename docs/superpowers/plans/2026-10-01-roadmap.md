# Implant Course Manager — Core Build Roadmap

Spec: `docs/superpowers/specs/2026-10-01-implant-course-manager-design.md`

The Core spec is delivered as five plans, each producing working, tested software. Each plan
is written after the previous one is built, so it can name real files and functions.

| # | Plan | Spec sections | Delivers |
|---|---|---|---|
| 1 | Foundation | 2, 3, 4.1, 4.8, 6 (Admin), 8 | Next.js app in `web/`, hosted dev DB + migration runner + DB test harness, profiles/roles/settings with RLS, audit log, login with email verification, invite acceptance, optional TOTP 2FA, idle timeout, app shell, Admin users + settings |
| 2 | Patients & odontogram | 4.2, 4.5 (`tooth_status` only), 6 (Patients, Odontogram) | Patient list/search, patient page opening on own odontogram, medical-alert header, Overview/Notes/History tabs, SVG odontogram with tooth statuses and bulk status |
| 3 | Inventory & implant lifecycle | 4.5 (sites, components, follow-ups), 4.6, 5.1, 5.4–5.7 | Catalog, receive stock (optional lot/expiry), ledger, `place_implant`, `fit_component`, `record_followup`, lot picker, component badges, recall lookup, adjust/waste |
| 4 | Courses, delegates & surgery schedule | 4.3, 4.4, 5.2, 5.3, 5.8 | Courses, delegates, enrollments, sessions, chairs (Admin), surgery slots with double-booking warnings, planned implants on chart, pull list, delegate report + CSV |
| 5 | Checklists & dashboard | 4.7, 5.9, 6 (Dashboard, Checklists) | Templates, paste-to-items, auto-attach to sessions/slots, tick/untick with attribution, Checklists section, Dashboard widgets |

## Changes after Plan 3

- **Delegates registry moved into Plan 3** (placement requires a placing delegate). Plan 4 adds
  courses/sessions/slots and links placements to them (`course_id`, `session_id`, `slot_id`).
- **Correction workflow (new, from Plan 3 final review I3) — schedule with Plan 4 or 5:** organizers
  must be able to correct a mis-recorded placement or outcome without editing the ledger:
  change the batch used at placement (reversing `use` movement + new one, keeping recall
  accurate, `reverses_movement_id`), undo a mistaken "failed" follow-up, and undo a final
  restoration entered by mistake — each audited, with a reason.
